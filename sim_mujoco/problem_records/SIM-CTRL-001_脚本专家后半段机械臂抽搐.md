# SIM-CTRL-001：脚本专家后半段机械臂持续抽搐

## 基本信息

- 日期：2026-08-12
- 分类：`SIM-CTRL`，逆运动学与轨迹控制
- 状态：已修复
- 影响范围：`SCRIPTED_EXPERT` 参考控制器，不影响 ACT/SmolVLA Policy 输出
- 首次发现产物：`outputs/scripted_expert_reference_v1_oscillatory.mp4`

## 现象

旧版视频中，SO-101 能夹住并抬起绿色方块，但进入横向搬运阶段后手臂明显来回跳动。方块在快速运动中提前滑落，机械臂随后仍不断追赶目标位置，因此后半段看起来持续“抽搐”。

抽搐不是视频帧损坏：机械臂在第三人称、Front 和 Wrist 三个同步视角中都发生相同运动，逐步 JSON 中的关节状态和动作也存在对应跳变。

## 先看小白版：它为什么会抽搐

### 第一步：机械臂其实在完成两个不同问题

让机械臂拿着方块移动，看起来只有一句话：

> 把夹爪移到目标位置。

但对控制程序来说，它包含两个问题：

1. **夹爪最终在哪里？** 例如向右20厘米、向上10厘米；
2. **整条胳膊应该摆成什么姿势？** 肘部朝左还是朝右，手腕转多少，肩膀绕多少。

旧控制器只回答了第一个问题，没有回答第二个。

### 第二步：同一个夹爪位置，可以对应很多种手臂姿势

你可以亲自做一个小实验：

1. 把右手食指放在桌面上一个固定点；
2. 保持指尖不动；
3. 尝试移动自己的手肘、肩膀或转动手腕。

你会发现：**指尖位置没变，但胳膊可以摆出很多姿势。**

SO-101 也一样。旧控制器只要求夹爪的三项位置正确：

```text
左右位置正确
前后位置正确
上下位置正确
```

但它同时允许5个手臂关节运动：

```text
肩膀左右转
肩膀上下抬
肘部弯曲
手腕弯曲
手腕旋转
```

可以粗略理解为：程序只出了3道题，却要求决定5个答案。多出来的2个答案没有唯一规定。

### 第三步：为什么不是“随便选一个姿势”就结束

旧程序每一帧都会重新计算一次姿势，而且没有告诉下一帧：

> 尽量保持上一帧的肘部和手腕姿势。

于是它可能发生这种情况：

```text
第1帧：选择“肘部偏左”的姿势
第2帧：发现“肘部偏右”也能让夹爪到达目标，于是切过去
第3帧：数值稍微变化，又切回“肘部偏左”
第4帧：再次切到“肘部偏右”
```

夹爪的目标位置可能相差不大，但肩、肘和腕来回换姿势，肉眼看到的就是抽搐。

### 第四步：旧版为什么在后半段特别明显

旧版还存在第二个问题：每个阶段直接瞄准很远的终点。

这就像开车时，导航只告诉你“立刻到达200米外的路口”，而没有生成中间平滑路线。控制器会急着追目标，关节每帧变化很大：横移阶段最大约 `3.13°/帧`。

机械臂拿着方块快速横移时，方块受到的晃动和接触冲击也更大，所以方块提前滑落。方块掉了以后，旧控制器不知道自己已经失去抓取，仍继续追赶目标，看上去就像后半段一直乱抖。

### 第五步：新版怎么修好——给它三条更明确的规则

新版不是“把抖动视频做平滑”，而是修改实际控制动作：

#### 规则一：一次只走一小段

在起点和终点之间生成平滑的中间位置：

```text
起点 → 很小一步 → 很小一步 → 很小一步 → 终点
```

这样机械臂不会突然追赶很远的目标。

#### 规则二：能保持原姿势就不要乱换姿势

如果多个手臂姿势都能让夹爪到达同一位置，新版优先选择最接近当前姿势的那个。通俗地说：

> 夹爪要完成移动，但肘部和手腕不要做没有必要的动作。

这就是文档后面提到的“零空间姿态保持”。名字听起来难，本质就是“不影响夹爪任务的多余关节，尽量别乱动”。

#### 规则三：每帧限制最大变化

旧版允许的单步变化较大；新版将求解器内部的单步关节增量上限从 `0.03 rad` 降到 `0.008 rad`。不用记弧度，只需看实测结果：

- 旧版横移最大变化：约 `3.13°/帧`；
- 新版横移最大变化：约 `0.19°/帧`；
- 大约降低94%。

### 一句话总结

> 旧版只管“手伸到哪里”，不管“胳膊应该保持什么姿势”，而且移动太急，所以关节在多个可行姿势之间反复跳动；新版增加平滑路线、姿态保持和速度限制后，机械臂就稳定了。

## 从生活语言过渡到工程术语

| 小白说法 | 工程术语 | 在本问题中的作用 |
|---|---|---|
| 夹爪要到哪里 | 任务空间位置目标 | 规定 x、y、z 三项位置 |
| 肩、肘、腕怎么摆 | 关节空间姿态 | 由5个手臂关节共同决定 |
| 多出来的可随意动作 | 冗余自由度/零空间 | 不改变夹爪位置，却可能造成乱摆 |
| 尽量保持当前姿势 | 零空间姿态约束 | 避免在多个逆解之间跳变 |
| 接近难摆的姿势时别放大动作 | 阻尼最小二乘 | 降低奇异位置附近的剧烈关节变化 |
| 中间一步一步走 | 平滑笛卡尔轨迹 | 避免直接追赶远端目标 |
| 每帧不能转太多 | 关节增量/速度限制 | 给控制动作设置硬上限 |

看到这里已经足够理解原因。后面的公式是给需要复核算法实现的人准备的，不懂矩阵可以直接跳过。

## 排除项

### 不是视频编码问题

- H.264 文件能被 `ffprobe` 正常解码；
- 三个视角中的物理运动同步；
- JSON 里的 `state_deg` 和 `raw_action` 同时发生高频跳变。

### 不是模型推理问题

该视频永久标注 `SCRIPTED EXPERT / NOT POLICY`。动作由脚本 IK 计算，不调用 ACT、Diffusion 或 SmolVLA checkpoint。

### 不是 MuJoCo 数值爆炸

- qpos、qvel 全程有限；
- 仿真没有 NaN/Inf；
- 物体和机械臂仍遵守接触、摩擦和重力；
- 问题集中出现在控制目标和逆解，而不是整个物理场景发散。

## 根因

根因是“任务维数小于控制自由度”而没有零空间约束：

1. 控制器只要求夹爪末端到达三维位置，即任务空间只有3个约束；
2. 参与求解的是 shoulder_pan、shoulder_lift、elbow_flex、wrist_flex、wrist_roll 共5个关节；
3. 因此至少存在两个不影响末端位置的自由度；
4. 旧版每帧重新使用位置 Jacobian 求逆，却没有保持腕部姿态或靠近上一关节姿态；
5. 当 Jacobian 条件变差或目标快速变化时，求解会在多个等价关节姿态之间跳动；
6. 旧版还直接追赶阶段终点，单帧关节增量上限约0.03 rad（约1.72°），结合执行器动态后实测可达到约3.13°/帧；
7. 快速横移放大接触冲击，方块提前滑落；控制器不知道抓取已经丢失，继续追踪目标，造成持续抖动观感。

简化表达：末端位置看起来差不多，但手腕和肘部“怎么摆”没有被规定，控制器不断换姿势。

## 修复方案

修改文件：[`scripts/05_run_expert_reference.py`](../scripts/05_run_expert_reference.py)

实施四项修复：

1. 使用三次 smoothstep 对阶段起点和终点进行平滑笛卡尔插值，不再一步追赶远端目标；
2. 使用阻尼最小二乘伪逆，正则项为 `3e-3`，降低接近奇异位形时的放大效应；
3. 加入零空间姿态保持项，使冗余自由度靠近阶段起始姿态；
4. 将单步关节增量限制从0.03 rad降为0.008 rad，并在 release/settle 阶段固定手臂目标。

核心形式为：

```text
J# = Jᵀ (J Jᵀ + λI)⁻¹
dq = J# · position_error + (I - J#J) · posture_error
```

其中第二项只调整不影响末端位置的零空间方向，用来防止肘部和腕部在等价逆解之间跳变。

修复没有：

- 焊接方块到夹爪；
- 瞬移抓取中的方块；
- 删除重力或碰撞；
- 降低或伪造成功判定；
- 把脚本专家结果计入 Policy 成功率。

## 防回归措施

后续修改专家控制器时，建议自动检查：

- 搬运阶段最大关节变化不得超过 `0.5°/控制帧`；
- settle 阶段最大关节变化不得超过 `0.05°/控制帧`；
- `pick_success` 与 `place_success` 必须分别为真；
- 搬运阶段方块高度不得提前跌回桌面高度；
- JSON 中 qpos/qvel/action 必须全程有限；
- 视频仍须标注 `SCRIPTED EXPERT / NOT POLICY`。

若问题再次出现，优先比较：

1. `raw_action` 相邻帧差；
2. `state_deg` 相邻帧差；
3. Jacobian 阻尼参数；
4. 单步 `dq` 限制；
5. 零空间 posture reference 是否在阶段开始时正确固定；
6. 方块是否已在搬运中失去夹持。
