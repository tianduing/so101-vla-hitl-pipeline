## 2. 小白版：GPU 到底在忙什么

### 2.1 把 GPU 想成一间教室

可以把一张 GPU 想成一间教室：

- **显存总量**：教室一共有多少个座位；
- **显存使用量**：已经有多少座位放了书包；
- **GPU 利用率**：老师这一秒是否正在讲课；
- **训练进程**：正在使用教室的班级。

教室里已经放满书包时，即使老师此刻没有讲话，另一个班也进不来。

这就是为什么会看到：

```text
GPU 利用率：0%
空闲显存：只有约 2.6 GiB
```

`0%` 只说明采样的这一瞬间没有执行大量 GPU 计算，不等于这张显卡无人使用。训练程序可能正在：

- 从硬盘读取下一批数据；
- 用 CPU 做数据处理；
- 等待其他 GPU 完成同一步；
- 保存 checkpoint；
- 做验证；
- 等待进程间通信。

在这些阶段，模型、优化器和中间数据仍然放在显存中，所以显存不会释放。

### 2.2 为什么不能硬塞进去

如果一个新任务需要 7 GiB，而显卡只剩 2.6 GiB，就像新班级需要 70 个座位、教室只剩 26 个座位。强行启动的结果通常是：

```text
CUDA out of memory
```

简称 CUDA OOM，也就是“显存不够”。它通常会导致当前训练进程退出。四卡同步训练时，只要其中一张卡 OOM，整个四卡任务都会失败。

## 3. 普通用户版：三步找到是谁占用了显存

以下命令都不需要 `sudo`。

### 第一步：看每张卡还剩多少显存

```bash
nvidia-smi --query-gpu=index,name,memory.total,memory.used,memory.free,utilization.gpu \
  --format=csv,noheader,nounits
```

各字段含义：

| 字段 | 含义 | 判断任务能否启动时的重要程度 |
|---|---|---|
| `index` | GPU 编号 | 用于选择显卡 |
| `memory.total` | 总显存 | 硬件上限 |
| `memory.used` | 已用显存 | 已经被占用多少 |
| `memory.free` | 空闲显存 | **最重要的启动条件** |
| `utilization.gpu` | 瞬时计算利用率 | 判断是否会争抢算力，不能单独判断空闲 |

这里的单位是 MiB。粗略理解即可：`1024 MiB ≈ 1 GiB`。

### 第二步：找到占显存的 PID

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_gpu_memory \
  --format=csv,noheader,nounits
```

PID 是 Linux 给每个运行中进程分配的编号。拿到 PID 后，就能继续查进程属于谁。

### 第三步：查询用户、启动时间和完整命令

假设 PID 是 `598139`：

```bash
ps -o user,pid,lstart,etime,%cpu,stat,args -p 598139
```

重点字段：

- `USER`：是谁启动的；
- `STARTED`：什么时候启动；
- `ELAPSED`：已经运行多久；
- `ARGS`：执行的程序和参数；
- `STAT`：进程当前状态。

一次查看多个 PID：

```bash
ps -o user,pid,lstart,etime,%cpu,stat,args \
  -p 598139,598140,598141,598142
```

注意：普通用户通常能看到进程命令，但未必有权限读取其他用户的训练日志、配置文件或 `/proc/<PID>/fd`。这是正常的 Linux 权限隔离。

## 4. 为什么“已经跑了 2 小时”不能推出“还剩 2 小时”

### 4.1 生活中的例子

只知道一辆车已经开了两小时，但不知道目的地在哪里，也不知道已经走了多少公里，就不能计算还要开多久。

训练也是一样。`ELAPSED=02:00:00` 只表示程序已经运行两小时，不包含计划总量。

### 4.2 计算 ETA 至少需要三个量

假设：

- 当前训练步数是 `s`；
- 总训练步数是 `S`；
- 最近一段时间的平均每步耗时是 `t` 秒。

最基础的剩余时间公式是：

```text
ETA = (S - s) × t
```

例如：

```text
当前步数 s = 30,000
总步数   S = 100,000
每步耗时 t = 0.8 秒

ETA = (100,000 - 30,000) × 0.8
    = 56,000 秒
    ≈ 15.6 小时
```

如果不知道 `s` 或 `S`，公式就无法计算。不能仅根据显存占用、GPU 利用率或进程已运行时间可靠地补出这两个数。

### 4.3 有日志时怎样估算得更准

训练日志如果包含类似内容：

```text
step=30000/100000 loss=0.124 step_time=0.80s
```

应优先用最近几十到几百步的平均耗时，而不是只用最后一步：

```text
平均每步耗时 = 最近 N 步总耗时 ÷ N
```

这样可以减少数据加载、保存 checkpoint 和验证阶段造成的瞬时误差。

一个更接近实际的公式是：

```text
总剩余时间
≈ 剩余训练步数 × 最近平均每步耗时
  + 剩余验证耗时
  + 剩余 checkpoint 保存耗时
```

### 4.4 没有日志时能做到什么程度

可以分成三档：

1. **有当前步数、总步数和步速**：可以给出较可信 ETA；
2. **只有 checkpoint 文件及其时间**：可以粗略推算速度和剩余时间；
3. **只有进程和显存信息**：只能证明任务仍在运行，无法可靠估算终点。

本次属于第三档。对方的配置、日志和 `/tmp` 进度监控脚本权限均为仅本人可读，因此本文不编造剩余时间。

## 5. 本项目采用的解决方案

### 5.1 总体流程

```text
启动纠错流水线
      ↓
每 60 秒读取四张 GPU 状态
      ↓
每张卡是否至少空闲 7,000 MiB，且利用率不高于阈值？
      ├─ 否 → 记录快照 → 等待 60 秒 → 再检查
      └─ 是 → 选择满足条件的四张卡
                    ↓
               启动四卡 FSDP 训练
                    ↓
               审计 checkpoint
                    ↓
               MuJoCo 闭环评估 10 次
                    ↓
               汇总结果并生成视频
```

实际负责等待和选卡的脚本是：

```text
scripts/run_distributed_when_ready.sh
```

完整纠错流水线入口是：

```text
sim_mujoco/scripts/run_corrected_pipeline.sh
```

后台服务名称是：

```text
so101-vla-corrected-pipeline.service
```

### 5.2 为什么阈值是 7,000 MiB，而不是“只要有一点就启动”

训练所需显存不是一个完全固定的数。模型刚加载完成后，后续反向传播还会创建梯度和临时张量，CUDA 本身也要保留工作区。如果只根据刚启动时的最低占用判断，很容易在训练数步之后才 OOM。

因此要保留安全余量。本项目当前把四卡纠错训练的门槛设置为：

```text
FSDP_MIN_FREE_MIB=7000
```

这表示每张参与训练的卡在启动前至少空闲约 7 GiB。它是结合当前任务显存需求设置的工程阈值，不是适用于所有模型的通用数字。

### 5.3 为什么四张卡必须同时满足条件

当前训练使用同步四卡 FSDP。可以把四张卡想成四个人一起抬桌子：每一步都需要协作，最慢或失败的那个人决定整组结果。

如果只有三张卡有足够显存、第四张没有：

- 第四张卡可能 OOM；
- 其余三张卡会等待第四张卡通信；
- 最终整个分布式任务失败，而不是自动退化成三卡继续。

因此判断条件是 `eligible=4/4`，不能是 `3/4`。

### 5.4 为什么不自动杀掉别人的任务

结束其他用户进程可能让对方数小时或数天的训练成果丢失，也可能破坏 checkpoint。共享服务器上，看到占用不等于拥有终止权限。

本方案遵循：

- 只读查询 GPU 与进程状态；
- 不向其他用户进程发送 `kill`；
- 不抢占已经分配的显存；
- 自动等待资源自然释放；
- 条件满足后自动继续本项目。

如果确实需要抢占，必须由服务器管理员或任务所有者明确协调。

## 6. 如何查看本项目有没有等到显卡

### 6.1 查看后台服务


- `active (running)` 且子进程是 `sleep 60`：正在等 GPU；
- 出现 `train_policies_fsdp.sh` 或多个 Python 训练进程：已经开始训练；
- `inactive (dead)`：流水线已经结束，或者未启动；
- `failed`：需要查看错误日志。

### 6.2 查看自动选卡日志

```bash
tail -f logs/system/fsdp_gpu_wait.log
```


逐段解释：

- `eligible=0/4`：四张卡中，目前零张满足条件；
- `min_free_mib=7000`：每张卡至少要求空闲 7,000 MiB；

## 7. 进阶原理：显存为什么一直占着，利用率却跳来跳去

一次训练迭代通常包含以下阶段：

1. CPU/DataLoader 准备一批数据；
2. 数据复制到 GPU；
3. 前向传播计算预测结果；
4. 根据预测与答案计算损失；
5. 反向传播计算梯度；
6. 多张 GPU 交换或聚合信息；
7. 优化器更新模型参数；
8. 定期保存 checkpoint 或执行验证。

参数、优化器状态和许多缓存会跨迭代保留在显存中，因此显存曲线通常比较平稳。计算和通信则是一阵一阵发生的，因此利用率可能在 `0%` 与 `100%` 之间快速跳动。

`nvidia-smi` 展示的是采样窗口内的情况，不是整段训练的平均情况。一次看到 `0%` 不能证明任务闲置。可以连续观察：

```bash
watch -n 1 nvidia-smi
```

不过即使连续许多次利用率较低，也只能说明算力使用效率可能不高；只要显存仍被进程持有，其他需要大量显存的任务就不能安全启动。

### 7.1 FSDP 在这里解决什么，不解决什么

FSDP 的核心思想是把大模型的参数、梯度和优化器状态分散到多张 GPU，而不是每张卡都保存完整副本。它可以降低单卡显存压力。

但 FSDP 不能：

- 把已经被别人占用的显存变成空闲显存；
- 保证任何大小的模型都不 OOM；
- 让四卡同步任务在任意一张卡失败后继续正常训练；
- 从系统进程信息推算另一个任务的结束时间。

所以正确顺序是：先确认资源阈值满足，再启动 FSDP。

## 8. 如果以后需要更可靠的 ETA，训练任务应该怎样设计

这是对我们自己任务的改进建议，不要求修改其他用户的任务。

### 8.1 日志必须记录的字段

每隔固定步数记录：

```text
timestamp
current_step
total_steps
steps_per_second 或 seconds_per_step
epoch
loss
next_checkpoint_step
estimated_finish_time
```

### 8.2 使用最近窗口计算，而不是全程平均

训练刚启动时会有模型加载、CUDA 初始化和缓存预热，最初几步通常较慢。使用最近 `100` 或 `500` 步的移动平均更能代表当前速度。

设最近 `N` 步耗时分别为 `t1, t2, ..., tN`：

```text
移动平均步耗时 = (t1 + t2 + ... + tN) / N
ETA = 剩余步数 × 移动平均步耗时 + 固定收尾耗时
```

### 8.3 ETA 必须标注为估计值

以下情况会让 ETA 变化：

- 定期验证比训练步骤慢；
- 保存大 checkpoint；
- 其他用户争抢 CPU、磁盘或 GPU 算力；
- 数据长度不一致；
- 网络或分布式通信波动；
- 训练中途 OOM、报错或重启。

因此更规范的展示方式是：

```text
预计剩余 3小时20分，误差约 ±25分钟
```

而不是承诺一个绝对准确的结束时刻。

## 9. 常见误区

### 误区一：GPU 利用率是 0%，所以可以启动

错误。还必须检查空闲显存。利用率表示瞬时计算忙碌程度，空闲显存才决定模型是否装得下。

### 误区二：四张卡的总空闲显存相加够用就可以

不一定。普通 CUDA 分配不能把四张卡自动拼成一块大显存；而同步四卡训练也要求每张卡各自满足最低需求。

### 误区三：程序已运行两小时，所以快结束了

错误。没有总步数和当前步数就无法知道完成比例。

### 误区四：`nvidia-smi` 显示 Python，所以查不出是谁

可以用 `nvidia-smi` 得到 PID，再用 `ps` 查询 PID 对应的用户和命令。

### 误区五：显存不够就直接杀进程

共享服务器上不能擅自结束其他用户任务。应先联系任务所有者或管理员，或者像本项目一样自动等待。

### 误区六：使用 FSDP/DeepSpeed 就不需要检查显存

错误。分片技术可以降低本任务的单卡需求，但仍然需要真实的空闲显存和运行余量。

## 10. 一页式操作清单

发现训练没有启动时，按下面顺序检查：

```bash
# 1. 每张卡还剩多少显存？
nvidia-smi --query-gpu=index,memory.used,memory.free,utilization.gpu \
  --format=csv,noheader,nounits

# 2. 哪些 PID 占用了显存？
nvidia-smi --query-compute-apps=pid,process_name,used_gpu_memory \
  --format=csv,noheader,nounits

# 3. PID 属于谁、跑了多久、执行什么命令？
ps -o user,pid,lstart,etime,%cpu,stat,args -p <PID>

# 4. 我们的自动流水线还活着吗？
systemctl --user status so101-vla-corrected-pipeline.service --no-pager

# 5. 四张卡中有几张满足启动阈值？
tail -n 20 logs/system/fsdp_gpu_wait.log

# 6. 训练启动或失败后，看流水线日志
tail -n 100 sim_mujoco/runs/corrected_pipeline_stdout.log
tail -n 100 sim_mujoco/runs/corrected_pipeline_stderr.log
```

最终判断规则：

| 观察结果 | 判断 | 处理方式 |
|---|---|---|
| 利用率低、空闲显存低 | 模型仍占着显存 | 等待，不启动 |
| 空闲显存够、利用率很高 | 装得下，但会争抢算力 | 根据策略等待或低优先级运行 |
| 四张卡均达到显存和利用率阈值 | 可以启动四卡训练 | 自动选卡并执行 |
| 只有部分卡满足条件 | 不满足同步四卡要求 | 继续等待或修改训练方案 |
| 有步数、总步数和平均步耗时 | 可以估算 ETA | 使用剩余步数公式 |
| 只有 PID、显存和已运行时间 | 无法可靠估算 ETA | 查日志或询问任务所有者 |
